# 設計案: 整形を3社同時に走らせる(2026-10-18、未実装)

> 状態: **設計案**。実装したら要点を `design.md` の先頭側へ節として移し、このファイルは消す。
> 決定者: ユーザー(2026-10-18)。画面テキストが3社へ毎回送られることは承知の上で、同時方式を選んだ。

## 1. 何を変えるか

今は **主 Gemini → (落ちたら) 控え Groq → 生転写** の直列。これを、**Gemini・Groq・OpenRouter を同時に投げ、優先順位と待ち期限で1つを採用する**方式に変える。

```
            ┌─ Gemini   (優先1) ─┐
生転写 ──┼─ Groq     (優先2) ─┼─▶ 採用規則 (§3) ─▶ 整形後テキスト / 生転写
            └─ OpenRouter (優先3) ┘
```

## 2. なぜ変えるか(実測、履歴DB 2026-09-18〜10-18、463件)

| outcome | 件数 | format_ms p50 | p90 |
|---|---|---|---|
| formatted(Gemini) | 424 | 1.17s | 1.65s |
| fallback_formatted(Groq) | 33 (7.1%) | **6.55s** | 7.36s |
| raw_fallback | 5 | 3.07s | 8.51s |

- 控えに回った33件のうち22件は Gemini のタイムアウトで、6秒の見切りを毎回待っていた。
- 生転写まで落ちた5件のうち3件は Groq 側の不具合(`length` 2件、空応答1件)。もう1社あれば救えていた。
- Groq がサービスとして落ちた記録(5xx・429・接続断)は整形では0件。

**同時に投げれば、Gemini が落ちたときの待ち時間は「Gemini の見切り」ではなく「待ち期限」で決まる。**

## 3. 採用規則(核心)

### 3.1 定義

- 優先順位: `Gemini (1) > Groq (2) > OpenRouter (3)`。キーが無い・無効の社は参加しない。
- 各社は `Ok(text)` か `Err(reason)` で**決着**する。決着しないまま絶対期限 `H` を過ぎた社は `Err(タイムアウト)` とみなす。
- 待ち期限 `T_pref`: 優先度の高い社を待つ上限。

### 3.2 規則

時刻 t で、次のどちらかが成り立った瞬間に決める:

1. **成功している社 i があり、i より優先度の高い社がすべて `Err` で決着済み** → i を採用(待つ相手がもういない)
2. **t ≥ `T_pref` で、成功している社が1つ以上ある** → 成功している中で最も優先度の高い社を採用
3. **全社が `Err`** → 生転写(R2 劣化モード。理由は全社分を書く)

`T_pref` を過ぎても成功が1つも無いときは、**最初に成功した社**を採用する(規則2が、成功が届いた瞬間に成り立つ)。

### 3.3 例

| 状況 | 結果 | 採用時刻 |
|---|---|---|
| Gemini 1.1s で成功(通常) | Gemini | 1.1s(今と同じ) |
| Gemini が 0.3s で 503、Groq 0.6s で成功 | Groq | 0.6s(規則1) |
| Gemini が無応答、Groq 0.6s で成功 | Groq | **2.0s**(規則2。今は6.5s) |
| Gemini 2.3s で成功、Groq 0.6s で成功 | Groq | 2.0s(Gemini の結果は捨てる。§7で記録) |
| Gemini・Groq 失敗、OpenRouter 0.5s で成功 | OpenRouter | 両者が決着した時点 |
| 全社失敗 | 生転写 | 最後の決着時点(最大 `H`) |

### 3.4 数値

| 定数 | 値 | 根拠 |
|---|---|---|
| `T_pref` | **2.0s** | Gemini の成功で 2.0s を超えたのは 17/424 = **4.0%**(1.5s だと 18.4% が Groq に流れる)。4%は Groq に譲っても質の損はほぼ無い(§4) |
| `H`(全社の絶対期限) | **8s** | 今の控えの期限と同じ。Gemini の成功で 6s を超えたのは 1/424 |
| 最悪の待ち時間 | **8s** | 今は 22.5s(主6 + 控え8 + 0.5 + 8) |

- 各社の HTTP タイムアウトは `H` に揃える。Gemini の `FORMAT_TIMEOUT_WITH_FALLBACK`(6s)は同時方式では使わない。
- **再試行は Groq だけ、`H` に収まるときに限って1回残す。** 条件は「経過 + 待ち(`Retry-After`、無ければ 0.5s)+ 1回分の見込み(1.2s、実測最大 1142ms)≤ `H`」。
  - **既定の構成では OpenRouter のキーが空なので、2社の並列になる。** 「ほかの社が埋める」が成り立たないので、Groq の再試行を外すと今より弱くなる。
  - Groq は毎回呼ばれるようになり、無料枠(毎分 8,000 トークン)の 429 が今より出やすくなる。1回のプロンプトの大きさは、システム指示が約1,000トークン、deep context が上限 2,000 文字(`MAX_CONTEXT_CHARS`)で約2,000トークン、と見積もった(日本語を1文字≒1トークンとした推測。履歴にトークン数は残っていない)。画面テキストが満杯なら、1分あたり2〜3件で枠に当たりうる。429 は「◯ms 後に再試行を」と待ち時間を返してくる類なので、1回待てば直る見込みが高い。
  - Gemini は `with_retry(false)`、OpenRouter も再試行しない。

## 4. 優先順位の根拠と、その弱さ

- Gemini を1位にしたのは今の主だから。Groq 20b は「原文に忠実」で選んだ(design.md M5)。**両者を実際の発話で比べたデータは無い。**
- OpenRouter(`nvidia/nemotron-3-super-120b-a12b:free`、思考なし)は 2026-10-18 の計測で一段落ちる。「〜なんですけど、〜」を「〜の〜」に畳んだ(10/10 回)。だから3位。
- 同時方式なら毎回3社の出力が手に入るので、**§7 の候補記録を2週間ほど貯めてから順位を決め直す。** 今の順位は暫定。

「返ってきた答えをその場で採点して選ぶ」案は採らない(§10)。

## 5. 実装の形

### 5.1 並列の走らせ方

- `TextFormatter::format` は同期(`reqwest::blocking`)のまま変えない。
- 各社を `std::thread::spawn` で走らせ、`mpsc` で `(provider, Result, elapsed)` を受け取る。呼び出し側は `recv_timeout` で §3 の規則を回す。
- **`thread::scope` は使わない。** scope は全スレッドの終了を待つので、採用後も遅い社の終了(最大 `H`)まで返れなくなる。採用した時点で返り、残りのスレッドはそのまま走らせて、自分のタイムアウトで終わらせる(切り離し)。
  - そのために整形器は `Arc<dyn TextFormatter>`、要求は所有型 `OwnedFormatRequest`(`String` と `Vec<DictionaryEntry>`)にする。
  - 後処理ワーカーは直列なので、次の録音と残りスレッドが重なることはある。HTTP を1本余分に持つだけで、状態は共有しないので害は無い。
- **採用規則は純関数として切り出す**: `decide(events: &[Settled], now, cfg) -> Option<Decision>`。時刻つきの決着の列を入れれば判定が出るようにして、スレッド無しで表形式のテストを書けるようにする(§9)。

### 5.2 OpenRouter の整形器

- OpenAI 互換なので、`GroqFormatter` を `OpenAiCompatFormatter` に一般化する。違いはエンドポイント、キー、提供元名、本文への追加フィールドだけ。
- 本文の組み立ては `format::system_prompt` / `format::user_message` を**そのまま**使う(主と同じ注入耐性・文体)。
- OpenRouter では `reasoning: { enabled: false }` を足す。**思考ありだと p50 7.2s、思考なしだと 0.48s**(2026-10-18 実測。出力トークンの約9割が思考だった)。
  - `reasoning: { effort: "low" }` も試したが、p50 7.3s で思考トークンも 190〜410 と減らなかった。中間は無い。
  - 計測は LIVE_SAMPLE だけで、プロンプトは約1,000トークン(辞書・画面テキスト無し)。本番で deep context が入ると入力は倍以上になり、OpenRouter が `H` までに返る割合は下がりうる。`T_pref` の根拠は Gemini の分布なので、こちらには影響しない。
- 応答のヘッダは生成完了より先に届くことがある(空白でつなぎ続ける)。所要時間は本文を読み切った時点で測る。2026-10-18 の計測で一度これを踏んだ。

### 5.3 結末の型と履歴

- `FormatOutcome::Formatted` = **優先1位を採用**。
- `FormatOutcome::FormattedByFallback { reason }` = **1位以外を採用**。`reason` は1位を採らなかった理由で、`期限 2.0 秒までに返らず` か、1位の失敗理由。`is_degraded()` は false のまま(小窓は静か)。
- **採用した社を記録する列を足す**: `sessions.format_provider TEXT`(`gemini` / `groq` / `openrouter`、旧行は NULL)。今は「fallback = Groq」が暗黙の前提だが、3社になると崩れる。移行は既存と同じく `ALTER TABLE ... ADD COLUMN`。
- **「遅かった」と「落ちた」を機械的に区別できるようにする**: `sessions.format_skip_kind TEXT`(`failed` / `slow`、1位を採用した行は NULL)。
  - design.md は「主が何日も落ちたまま誰も気づかない」の対策として、`fallback_formatted` の行を数えることにしている。
  - 同時方式では、Gemini が健全だが 2.0s を超えた録音(約4%)も `fallback_formatted` になる。区別が無いと、この件数は「Gemini が落ちていた」を意味しなくなる。
  - `failed` だけを数えれば、今の数え方の意味が保たれる。
- 全社失敗の `RawFallback.reason` は、優先順に全社の理由をつなげる。小窓は最初の「:」で切るので、先頭は1位の理由にする(今の規則を維持)。
- 遅れて届いて捨てた結果は `log::info!` に社名と所要時間だけ残す(本文は出さない)。

## 6. 設定

| 項目 | 既定 | 備考 |
|---|---|---|
| `format_strategy` | `"parallel"` | `"sequential"` で今の直列に戻せる。旧設定ファイルには無いので、フィールド単位で `serde(default)` を付ける |
| `format_fallback_enabled` | true(既存) | 「Groq を整形に参加させるか」の意味に読み替える |
| `openrouter_api_key` | 空 | 空なら OpenRouter は参加しない |
| `openrouter_format_model` | `nvidia/nemotron-3-super-120b-a12b:free` | 候補つき入力欄 +「試す」(既存の `test_format_model` を拡張) |
| `openrouter_chat_endpoint` | `https://openrouter.ai/api/v1/chat/completions` | 完全な URL |

- **キーを読む環境変数の名前に注意。** Groq・Gemini は「環境変数 > 設定」の順でキーを解決している。今の `OPENROUTER_API_KEY` には**課金していない方のアカウントのキーが入っている**(1日50回の枠、2026-10-18 確認)。同じ名前を採ると、設定画面に課金済みのキーを入れても環境変数が勝つ。**環境変数名は `NOX_OPENROUTER_API_KEY` にする**か、環境変数を読まない。
- `:free` モデルはよく入れ替わる(2026-10-18 の一覧16個のうち、作成2日目のものや agentic harness 専用で 403 になるものがあった)。既定のモデルが消えても、OpenRouter が毎回 `Err` で決着するだけで、ほかの2社には影響しない。消えたことはログと履歴の失敗理由で追える。

## 7. 候補記録(第2段で実装)

順位を実データで決め直すため、**3社すべての結果**を残す。

- 表 `format_candidates(session_id, provider, ok, ms, text, reason)`。ローカルの SQLite だけに置き、外へは送らない。
- 遅れて届いた結果も入れたいので、採用とは別に「全社が決着するまで(最大 `H`)待って書く」収集役を置く。履歴の行は注入の前に書く(R4)ので、`session_id` は後から収集役へ渡す。
- 保持期間は履歴本体の WAV/行の寿命(M4)に合わせる。
- 2週間ほど貯まったら、3社の出力を並べて比べる(人が見るか、オフラインで LLM に判定させる)。結果で §4 の順位を決め直す。

## 8. プライバシーと枠(R1 の拡張)

- **毎回**3社へ整形プロンプト一式を送る: 生転写・辞書・文体、deep context が ON なら**画面のテキスト**も。送り先は Google、Groq、OpenRouter とその先の提供元(既定モデルなら NVIDIA)。
  - 今は、Groq へ行くのは主が落ちたときだけ。同時方式では常時になる。
  - 既定モデルの無料エンドポイント(提供元 NVIDIA)は、OpenRouter のモデルページに次の旨を掲げている(2026-10-18 確認): 利用は記録され、セキュリティと NVIDIA の製品・サービスの改善に使われる。記録は本人の識別子とは結び付けない。機密や個人情報は送らないこと。保持期間と、訓練に使うかどうかの明記は無い。**R1(Gemini 無料枠)と同じ種類の、受け入れが要るリスクである。**
- 設定画面の、控えのトグル直下にある警告文を3社版に書き換える。`format_strategy` の切り替えの隣にも同じ警告を出す。
- 枠(1日の最多は53件、2026-09-26):
  - Gemini は今も毎回呼んでいるので、増えない。
  - Groq は整形の呼び出しが毎回になり、STT と合わせて約2倍。gpt-oss-20b の無料枠は毎分 8,000 トークン(format_groq.rs の doc)。連続で録音したときの 429 は、ほかの2社が埋める。
  - OpenRouter は1日 53 回で、課金済みアカウントの枠(1,000回/日、毎分20回)に十分収まる。課金していない方の50回/日でも、多い日は足りなくなる。
- 画面質問モードは変えない(画像を送るので、テキスト専用の控えは使えない)。

## 9. テスト

- **採用規則(純関数)**: §3.3 の表をそのまま表形式のテストにする。境界も入れる: `T_pref` ちょうどに届いた場合、全社が同時に決着した場合、参加者が1社だけの場合、キーが無くて OpenRouter が不参加の場合。
- **並列の実行部**: 遅延と結果を指定できる偽の整形器で、次を確かめる。
  - 採用後すぐ返る(遅い社の `H` を待たない)
  - 全社失敗で生転写に落ち、理由が優先順に並ぶ
- **数値を固定するテスト**: `T_pref` が実測 p95 より上にあること、最悪の待ち時間が `H` 以下で今の 22.5s より短いこと。
  - 既存の `the_primary_deadline_sits_just_above_the_observed_p99` / `adding_a_second_rung_did_not_make_the_tail_worse` は `sequential` の数値としてそのまま残す。同時方式のものは別に足す(置き換えない)。
- **Groq の再試行**: `H` に収まらないときは試し直さないこと。収まるときは1回だけ試し直すこと。
- **実 API**(`#[ignore]`): 3社を同時に投げて、規則どおりに採用されること。キーが無い社はスキップする。
- 検証ゲートはローカルの5ステップ(ビルド・テスト・疑似 E2E・実機)。

## 10. 採らなかった案

| 案 | 採らなかった理由 |
|---|---|
| 段階起動(Gemini を投げ、1.5s で返らなければ Groq も) | 送信先と呼び出し回数は小さく済むが、ユーザーが同時方式を選んだ(2026-10-18)。待ち時間の差は約1s |
| その場で採点して最良を選ぶ(LLM に判定させる) | 判定のためにもう1往復かかり、遅くなる。判定役の失敗という新しい壊れ方も増える |
| 3社の出力を混ぜる・多数決 | 整形は1つの正解に収束しないので、多数決が成り立たない。混ぜると「発話を足さない」の保証が崩れる |
| 返ってきた中で最速を採用する | 優先順位が意味を失う。毎回、最速だが一段落ちる社(nemotron)が採られがちになる |

## 11. 実装の順序

1. `OpenAiCompatFormatter` への一般化と、OpenRouter の設定・キー・「試す」(順序は今の直列のまま、第3段として動く状態)
2. 採用規則の純関数、並列の実行部、`format_provider` 列、`format_strategy`
3. 設定画面の警告文と、履歴バッジの採用社表示
4. 候補記録(§7)
5. 2週間後に順位を決め直す

## 12. 決めてほしいこと

- 優先順位は暫定で `Gemini > Groq > OpenRouter` とした。今は比べたデータが無い。
- `T_pref` は 2.0s とした。代わりに、**録音の約4%は何も失敗していないのに Groq の結果が採られ、履歴に「控えで整形」と残る**(`format_skip_kind = slow` で区別はできる)。
- 既定モデルの無料エンドポイント(NVIDIA)は、利用を記録して製品改善に使うと明記している(§8)。これを受け入れるか。
- 候補記録(§7)で、3社の出力本文をローカルの DB に残してよいか。
- OpenRouter のキーを環境変数から読むなら、名前は `NOX_OPENROUTER_API_KEY` にする(§6)。
