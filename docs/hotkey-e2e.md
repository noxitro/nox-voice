# ホットキー経路の E2E と、そこで直した不具合 (2026-08-26 / 08-28)

## 走らせ方

```bash
npm run e2e:hotkey
```

`src-tauri/target/debug/nox-voice.exe` を実際に起動し、実キー相当の合成入力
(`SendInput`) を送って、**アプリのログに何が出たか**で判定する。設定 UI の操作は
WebView2 の CDP (`--remote-debugging-port`) から行う。

前提と副作用:

- **実設定ファイルを使う**。開始時に `config.json.e2e-backup` へ退避し、終了時
  (異常終了も含む) に必ず戻す。
- 走行中は `injection_enabled` を切る。合成キーで始まった録音の結果が
  利用者の作業中ウィンドウへ貼られるのを防ぐため。
- **送ったキーは前景アプリにも届く**。PTT のキーは `send-keys.ps1 -Sink` が出す
  E2E 自身の空ウィンドウを前景にしてから送る (実際の使われ方 = 他のアプリが前景、を
  作るため)。前景奪取は成功しないことがある (バックグラウンドのコンソールから起動した
  プロセスは前景を取れない) ので、そのときは前景のアプリへ流れる。
  トリガーは物理キーボードに存在しない F13〜F15 を主に使うが、既定ホットキーの
  検証だけは Space を送る。**実行中はキーボードに触らないこと。**
- デバッグビルドは `frontendDist` ではなく `devUrl` を見るので、ハーネスが
  vite を起動する。上がっていないと画面が真っ白のまま起動し、エラーも出ない。

## 2 つの入力経路 (2026-08-28 から)

キー捕獲が DOM の `keydown` / `keyup` へ移ったので、ハーネスが送るキーも
**2 系統**になった。どちらで送るかがそのままテストの意味を決める。

| 経路 | 送り方 | 通る道 | 使うテスト |
|---|---|---|---|
| フック経路 (PTT) | `SendInput` (`send-keys.ps1 -Sink`、E2E の空ウィンドウが前景) | OS → `WH_KEYBOARD_LL` → Rust | T1 / T2 / T4 / T5 / T6 / T9 |
| フック経路 (PTT、nox-voice が前景) | `SendInput` (`send-keys.ps1 -FocusPid`) | 同上 | T1w (下の「Chromium 系のウィンドウが前景だとフックが呼ばれない」) |
| DOM 経路 (捕獲) | CDP (**接続直後に実測して**選ぶ、下記) | webview → `src/main.ts` → invoke → Rust | T3 / T7 / T10 |

DOM 経路の送り方は**決め打ちしない**。`Input.dispatchKeyEvent` はレンダラの
入力パイプラインを通るので本来こちらが望ましいが、WebView2 では **`code` が
空のまま DOM へ届く**ことが実測で分かった。捕獲は `event.code` だけを見るので、
Esc が `Unidentified` になって取り消しが効かず、`T7` が捕獲を開いたまま素通りし、
その残骸が次の `T10` を巻き添えにして落ちた。

そこで `T0` で **1 打送って `code` が届くか確かめ**、届かなければ
`KeyboardEvent` の合成へ落とす (`Cdp#detectKeyTransport`)。どちらを使ったかは
`T0` の結果行に出る。**どの経路で緑になったのか分からない緑は信用しないこと。**

同じ理由で、**捕獲を始めるテストは「キー捕獲モード: 開始」のログが出たことを
必ず判定に含める**。前のテストが捕獲を開いたまま終わると、次のテストの
`#hotkey-capture` の click は「畳んで終わり」になり、キーがどこにも届かないまま
素通りで緑になる。

捕獲の開始では、**アプリ自身も 1 打送る**。フックの生存確認のダミーキー
(`VK_NONAME`、`hotkey::ensure_hook_alive_async`) で、合成キーなので前景の
ウィンドウにも届く。ボタンを押した直後は設定画面が前景なので、これが捕獲に
入ると `code` が空のまま拾われ、押してもいないのに「このキー (Unidentified) は
ホットキーに使えません」と出ていた (2026-09-26、画面が必ず前景になる CI で発覚。
手元の E2E ではハーネスが前景を取れないことが多く、ダミーキーは別のウィンドウへ
行っていた)。捕獲は `keyCode` が `VK_NONAME` のキーを数えない。`T3a` は捕獲を
開いてダミーキーが届き終わるまで待ち、何も拾っていないことを見る
(設定画面が前景でなければ測れないので、前景だったかを結果に書く)。
疑似 E2E の `U2e` は WebView2 に届く形のイベントで同じことを確かめる。

DOM 経路を CDP から入れるのは、**DOM へ届くにはアプリのウィンドウが前景で
なければならない**ため。このハーネスはバックグラウンドのコンソールから
起動するので前景を取れないことが多く、`SendInput` の合成キーは前景の
別アプリへ行ってしまい捕獲には 1 打も届かない。CDP なら前景に関係なく
webview の入力経路へ入れられる。

この作りの帰結:

- **捕獲系テストはフックの生死に依存しない。** `T1` が SKIP になる環境でも
  `T3 / T7 / T10` は判定できる (だから `needsInjectedKeys = false`)。
  これは仕様どおり — 捕獲をフックから切り離したのが今回の修正そのもの。
- **測れないこと**: 物理キーが OS → WebView2 → DOM と届くこと自体。
  ここは前景を取れる実機でしか確かめられない。`T3` が緑でも、
  **実機で設定ウィンドウを前面にしてキーを押す確認は省けない**。
- 同じ理由で、Win キーとの組み合わせ・PrintScreen のように OS が先に
  処理してしまうキーが「捕獲できない」ことも、ここでは再現できない。

## 判定の 3 値: PASS / FAIL / SKIP

`T1` (既定 左Ctrl+Space) は**較正を兼ねる**。ここが通らない環境では合成入力が
フックまで届いていないので、以降のキー依存テストは `FAIL` ではなく `SKIP` と
書く。**SKIP は合格ではない。** その run はキー経路について何も測れていない。

この区別が要るのは、実測で「物理キーボードでは動くのに、合成入力だけがフックに
届かない」状態が起きたため。SKIP のまま報告を終えず、物理キーで切り分けること。

陰性側のテスト (`T2` Space 単独 / `T5` 旧ホットキー) は、
**フックが死んでいても素通りする**。緑だけを見て安心しないこと。
`T7` (Esc 取り消し) は DOM 経路になったので、いまは「取り消しログが出たこと」も
併せて見る (何も起きなかっただけの素通りと区別するため)。

## 直した不具合 (すべて陽性コントロール付き)

陽性コントロール = 修正を元に戻して、対応するテストが**実際に落ちる**ことを確認した。

### 1. 合成入力を一律で無視していた → 正当なユーザー入力まで捨てていた

`WH_KEYBOARD_LL` の `LLKHF_INJECTED` で弾いていた。このフラグは注入元を区別しない
ので、RDP・PowerToys Keyboard Manager・AutoHotkey 等を経由した**本物のキー入力も
全部無視**される。`dwExtraInfo` に載せた自プロセスの印だけで判別するようにした。

- 陽性コントロール: 一律除外に戻すと `T1 / T3 / T4 / T6` が落ちる (4/8 → 8/8)。
- `docs/design.md` に「将来こう直す」と書いてあった既知の制限を実装した形。

### 2. 捕獲 UI で設定した直後から、そのホットキーが効かない

捕獲は「押したキーを**すべて離した瞬間**」に確定する。その確定処理が、確定した
全キーを「離されるまで無視」リストへ登録していた。登録解除は keyup でしか起きない
のに、**その keyup はもう過ぎている**。結果、設定したばかりのホットキーが
アプリ再起動まで恒久的に無視される。

「設定は保存されるのに効かない」という報告の正体。押されたままのキーだけを
登録するよう変更した。

- 陽性コントロール: 修正を戻すと `T4` だけが落ちる。
- 回帰テスト: `hotkey::tests::keys_already_released_are_not_suppressed`。
- 既存の単体テスト 2 本が**古い挙動を正しいものとして守っていた**ので、
  「押されている」をテストから注入できる形に直した (`hold_keys`)。

### 3. フックが OS に無言で外される

コールバックの応答が `LowLevelHooksTimeout` を超えると、Windows は
`WH_KEYBOARD_LL` をチェーンから落とす。通知も無く `UnhookWindowsHookEx` も
呼ばれないので、**アプリは正常に見えたまま全キーが届かなくなる**(再起動で直る)。

15 秒ごとの生存確認を入れた。無操作の間だけ `VK_NONAME` (0xFC) を 1 打自分宛に
送り、自分のフックが観測できなければフックスレッドへ再設置を要求する。
フックスレッドは `THREAD_PRIORITY_TIME_CRITICAL`。

- 検出できていることの証拠: ログに
  `キーボードフックが応答しません … 再設置します` が実際に出る。
- **未解決**: 再設置しても合成入力が戻らない run がある。同じ状態でも
  **物理キーボードでは正常に動く**ことを実測で確認済み (2026-08-26)。
  合成入力側の制約 (注入元プロセスの整合性レベル等) が疑わしいが未確定。

### 4. 多重起動していた

単一インスタンスの仕組みが無く、実際に 2 プロセス同時稼働を観測した。
トレイ常駐はウィンドウが見えないので気づけない。二重に起動すると:

- フックが 2 本刺さり、1 回の押下で**録音が 2 回**始まる
- 片方で設定を変えても、もう片方は古いホットキーで反応し続ける
- 設定ファイルとログファイルを奪い合う (**ログが切り詰められるのを観測**)

`tauri-plugin-single-instance` を、他のプラグインより前に登録した。

- テスト: `T8`。

**2026-08-27 追記**: プラグインだけでは漏れることが分かった (起動競合と昇格レベルの
不一致。詳細は `docs/design.md`「多重起動の確実な防止」)。`run()` の 1 行目で
名前付きミューテックスを取るようにし、実プロセス 2 個での確認は専用ハーネス
`e2e/single-instance.mjs` (`npm run e2e:single-instance`) に分けた。
このハーネスも開始時に `nox-voice.exe` を全部落とすので、**アプリを使っている間は
走らせないこと**。なお `hotkey.mjs` は起動前に taskkill するため、ミューテックス化の
影響を受けない (「既に起動中」と判定されて即終了することはない)。E2E 用の
抜け道は用意していない — 常用の抜け道は本番でも付けっぱなしになりうるため。

### 5. キー捕獲がフックの脱落に巻き込まれて完全に沈黙する (2026-08-28)

実機ログで、捕獲モードに入ってユーザーがキーを押しても**フックからの捕獲
イベントがプロセス起動から累計 0 件**という状態が再現した。同じフックで
PTT (左Ctrl+Space) は動いており、捕獲ウィンドウの間には必ず
「生存確認のキーを観測できない → 再設置します」が挟まっていた。

原因は `WH_KEYBOARD_LL` の**無言の除去**。[LowLevelKeyboardProc][llkp] は
「Windows 7 以降、タイムアウトしたフックは呼ばれずに黙って外される。
外されたことをアプリが知る方法は無い」と明記している。しかもタイムアウトの
計測対象はコールバックの実行時間ではなく**フックスレッドへのメッセージ送達→
応答の往復全体**なので、コールバックがいくら速くても、CPU が飽和して
フックスレッドがスケジュールされなければ外される (`THREAD_PRIORITY_TIME_CRITICAL`
でも免除されない)。このマシンでは cargo ビルドと E2E を並行実行していた。

加えて構造的欠陥として **捕獲ウィンドウ 10 秒 < 番犬の周期 15 秒** があり、
「フックが死んでから番犬が気づくまで」に捕獲窓がすっぽり収まっていた。

対策は捕獲を DOM イベントへ移すこと (`docs/design.md` の同日の節)。捕獲は
設定ウィンドウにフォーカスがある場面の操作なので、グローバルフックを使う
必然性が無い。テスト側もこれに合わせて 2 経路構成にした (上記)。

- 回帰テスト: `hotkey::tests::capture_mode_mutes_the_ptt_path_entirely`
  (捕獲中に現行ホットキーを押しても録音が始まらない) /
  `dom_codes_map_to_the_virtual_keys_the_rest_of_the_module_expects` /
  `mapped_codes_round_trip_through_the_existing_labels_and_rules` /
  `an_unmappable_code_is_reported_rather_than_silently_dropped`。
- 疑似 E2E: `sim-ui.mjs` の `U2` (押して離すと確定) / `U2b` (使えないキーは
  理由を出して捕獲を続ける、2 回続けても終わらない) / `U2c` (捕獲ボタンの
  click 直後、**IPC 完了前**に押したキーも取りこぼさない)。

### 5-2. 捕獲開始が非同期で、その往復の間のキーが素通りしていた

上の修正の初版で踏んだ。`capturingMode` を `await invoke("start_hotkey_capture")`
の**後**で立てていたため、IPC の往復の間だけキーを受け付けられない時間帯が
でき、そこで押された Space が `preventDefault()` されずに捕獲ボタンを再発火させ、
**捕獲が即座に取り消されていた**。詳細と一般形は `docs/design.md`
「状態フラグを IPC の後にセットすると、その往復の間だけ無防備な時間帯ができる」。

- 回帰テスト: `sim-ui.mjs` の `U2c`。**モックの invoke に遅延を注入**して
  (`mock.delays[cmd]`)、click の応答を待たずにキーを押す。
- 陽性コントロール: 修正前に実際に落ちることを確認した
  (`downPrevented:false` / `activeElement:"hotkey-capture"`)。
  **モックが即座に解決するテストでは、この種の不具合は永久にすり抜ける。**
- 実機 E2E: `T3` (DOM 捕獲で設定) / `T7` (Esc 取り消し) / `T10` (Enter を拒否)。

[llkp]: https://learn.microsoft.com/en-us/windows/win32/winmsg/lowlevelkeyboardproc

## 一覧選択の実機往復 (`npm run e2e:picker-live`、2026-09-01)

`e2e/hotkey-picker-live.mjs`。ホットキーの「一覧から選ぶ」を**本物の Rust 相手に**
往復させる。疑似 E2E (`sim-ui`) はモックなので `list_hotkey_keys` /
`describe_hotkey_vks` / `set_hotkey_from_list` の綴りがずれても緑になる — この穴を
塞ぐために、release ビルドを起動して CDP で実 DOM を操作し、結果を**アプリのログ**
(Rust 側の事実) で判定する。マウスには触れない。

| ケース | 見ているもの |
|---|---|
| P0 / P1 | 貼り付け用を F15 → F13 と**実際に変える**。同値への再設定は Rust が正しく「変更なし」にするのでログが出ない — 必ず変わる操作にしてある |
| P2 | クリップボード用にわざと F13 → `normalize` が重複を落とし、帯と一覧内の注記に理由が出て**一覧は開いたまま** |
| P3 | クリップボード用を F14 に (別用途への設定) |
| P4 | 往復のあいだページに例外が無い |

**副作用**: `nox-voice.exe` を強制終了して自分で起動し、**本物の config.json を書き換える**
(P2 が意図的に重複を作る)。終了時に「貼り付け」「クリップボードのみ」の 2 用途だけを
診断前の値へ戻す。**スナップショット丸ごとの書き戻しはしない** — 一度それで
別の変更 (F14) を消した。作業中のマシンでは走らせず、終わったら自分でアプリを起動し直す。

ログ判定の罠: ログ位置をバイト数で控えて文字列 `slice` すると、日本語 (1 文字 3 バイト)
で位置が先へずれて直近の行を読み飛ばす (実際に起きた。run ごとに結果が変わる)。
バイト列のまま `subarray` してから復号すること。

## Chromium 系のウィンドウが前景だとフックが呼ばれない (2026-09-26、未解決)

**症状**: nox-voice 自身の設定画面 (WebView2) が前景のあいだ、ホットキーを押しても
録音が始まらない。キーは設定画面の DOM には届いているのに、`WH_KEYBOARD_LL` の
コールバックが 1 度も呼ばれない。エラーも通知も無い。番犬の生存確認も同じ理由で
失敗し、再設置を繰り返しても変わらない (起動からフックが観測したキーイベントは 0 件)。

**CI で確かめたこと** (GitHub Actions の Windows ランナー、Windows Server 2025):
- 同じキーを、E2E 自身の空ウィンドウを前景にして送ると発火する
- 前景 (nox-voice の `Tauri Window`)・キーボードフォーカス (msedgewebview2.exe の
  `Chrome_WidgetWin_1`)・nox-voice はいずれも整合性レベル High・UIAccess なし。UIPI ではない
- 別のプロセス (`probe-input.ps1`) が LL フックを入れているあいだは、**nox-voice の
  フックにも届く** (そのあいだに送った 3 打の押下と離し 6 件を、nox-voice のフックが
  数えていた)。外すとまた届かない
- 他のフックが無い機械 (CI のランナー) では毎回起きる。常駐ソフトなどが LL フックを
  入れている機械では起きないことがあり、手元で再現しなかった理由と考えられる

同じ現象は、同じく WebView2 の設定画面を持つ押して話す型のアプリで報告されている
("Windows silently stops delivering WH_KEYBOARD_LL hook events when a Chromium window
has focus (and the diagnostic hook hides it)",
https://dev.to/wudaming00/windows-silently-stops-delivering-whkeyboardll-hook-events-when-a-chromium-window-has-focus-and-bi8)。
そこでも「診断用に 2 本目のフックを入れると両方に届くようになる」ことが観察されている。
仕組みは文書化されていない。

**影響**: ホットキーを設定した直後に、その画面のまま押して試すと効かない
(`hotkey::ensure_hook_alive_async` の doc が想定している使い方そのもの)。他社の
Chromium 系アプリ (ブラウザ・Electron) が前景のときに同じことが起きるかは、CI の
参考計測 (`NOX_E2E_EDGE=1`: Edge を前景にして押す) で見ている。

**E2E での扱い**: PTT のテストは実際の使われ方 (他のアプリが前景) で測り、nox-voice が
前景の場合は `T1w` で別に測る。`T1w` は直るまで FAIL になる。

**直し方の案** (上の報告と同じ方針): 設定画面にフォーカスがあるあいだは、ページの
`keydown` / `keyup` から Rust の同じ状態機械へキーを渡し、フック側はそのあいだ解釈を
止める (二重に発火させないため)。捕獲 (DOM 方式、2026-08-28) と同じ作りに寄せる。

## CI (GitHub Actions) で走らせる (2026-09-25)

実機 E2E 3 本 (`single-instance` / `picker-live` / `hotkey`) は、CI の `e2e` ジョブが
Windows ランナー上で毎回走らせる。ランナーは使い捨ての VM なので、「作業中のマシンでは
走らせない」理由になっていた副作用 (taskkill、本物の config.json の書き換え、前景への
合成キー) がここでは問題にならない。むしろ一番安全に走らせられる場所になる。

ランナーでは次のように走らせている。

- **exe は `NOX_E2E_EXE` で渡す。** `tauri build --no-bundle` で作ったリリース構成の exe を
  3 本とも測る。リリース版は `frontendDist` を同梱するので vite が要らず、配布物と同じ
  構成を測れる (`hotkey.mjs` は念のため vite も起こすが、リリース版は見に行かない)。
- **設定ファイルが無い状態から始まる。** 各ハーネスは「開始時に無かった」ことを覚えておき、
  終了時に作られた設定ファイルを消して元へ戻す。
- **録音デバイスが無い。** GitHub のランナーには音声デバイスが 1 台も無いので、
  `audio::start` が `録音を開始できません: 録音デバイスが見つかりません` で失敗する。
  `hotkey.mjs` は `NOX_E2E_NO_AUDIO=1` で走らせ、この行を「ホットキーが発火した」証拠として
  数える。**測れなくなるもの**: 録音の確定 (T1 の後半)、T11 (単独 Alt のダミーキー。
  停止側のログで数える)、T12 (小窓の表示区間)。これらは実行せず、最後の集計に
  「測っていない」と書く。

- **合成入力がフックまで届くかは、先に OS だけで確かめる。** CI は `e2e/probe-input.ps1`
  (自分でフックを刺し、自分でキーを送り、届いた数を数える) が `blocked` なら `hotkey.mjs` を
  `NOX_E2E_NO_INJECTION=1` で走らせる。このモードではキーを送らず、キー送出を要する
  テスト (T1 / T1w / T2 / T4 / T5 / T6 / T9) は結果を見ずに SKIP と書く。測るのは CDP から
  DOM へキーを入れる捕獲系 (T3 / T7 / T10)、アプリ自身のダミーキーが捕獲へ混ざらないか
  (T3a)、再起動後に保存値でフックが張られたか (T6b、起動ログのホットキー表示で見る)、
  多重起動 (T8)。ランナーはいまのところ `reachable` なので、全項目を測っている。

  probe はフックを**別スレッド**に刺して GetMessage を回し、キーは元のスレッドから送る
  (アプリと同じ形)。最初の版はフックを刺したスレッド自身から送っていたので、アプリと
  違う経路を測っていた (同じスレッドなら、スレッドをまたぐ LL フックの呼び出しを通らずに
  済む)。同じスレッドの結果は参考として並べ、`SendInput` の所要時間・`LowLevelHooksTimeout`
  の値・前景とフォーカスのウィンドウとプロセスのトークン (整合性レベル・昇格・UIAccess) も
  出す。T1 が落ちたときは、アプリが起動している状態で測り直して結果行に添える。

  最初の CI で「アプリのフックに合成キーが届かない」とされていたのは、環境ではなく
  上の「Chromium 系のウィンドウが前景だとフックが呼ばれない」だった (キーを
  nox-voice の設定画面が前景の状態で送っていた)。アプリ側も、番犬の警告に「起動から
  フックが観測したキーイベントの件数・再設置の回数」を添える。再設置を繰り返しても
  0 件のままなら、途中で外れたのではなく最初から 1 度も呼ばれていない。
- **管理者権限で走る。** ランナーはジョブを管理者権限 (High IL) で走らせる。昇格したホストでは
  WebView2 が `WEBVIEW2_*` の環境変数と HKCU の上書きを**無視する** (Microsoft
  "Develop secure WebView2 apps")。ハーネスが環境変数で付ける `--remote-debugging-port` が効かず、
  最初の CI では picker-live / hotkey が「CDP に繋がらない」で落ちた (ブラウザプロセスの引数に
  wry の `--disable-features=…` しか無いことを診断で確かめた)。昇格していても読まれる HKLM の
  ポリシー `…\Edge\WebView2\AdditionalBrowserArguments` に exe 名で渡す
  (`e2e/webview2-debug-port.ps1`)。ポートはハーネスごとに変え、`NOX_E2E_CDP_PORT` で知らせる。
  **使い終わったら必ず消す** (CI は `always()` で消す)。残すと普段使いのアプリまで localhost に
  デバッグポートを開く。手元でも管理者のターミナルから走らせると同じことが起きる。
- **CDP に繋がらないときは、その場で材料を出す** (`e2e/cdp-diagnose.mjs`)。ポートが応答するか、
  ターゲットの一覧、WebView2 のブラウザプロセスの引数 (`--remote-debugging-port` が付いているか) と
  待ち受けポート、管理者権限で動いているか。ランナーは後から覗けないので、落ちたログだけで
  次の手を決められるようにしてある。

判定の needle について: 録音開始を `録音開始` の部分一致で探すと、フォーカス診断が
`audio::start` の**前**に出す `[focus] 録音開始 直前` にも当たる。録音デバイスが無い run で
「開始した」と誤読するので、本物の開始行 `録音開始 [` で探す (`STARTED`)。

**CI が緑でも実機確認は省けない。** 物理キーが OS → WebView2 → DOM と届くこと、録音の確定、
T11 / T12、昇格ケースは、今までどおり実機でしか確かめられない。
