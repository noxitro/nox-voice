# ホットキー経路の E2E と、2026-08-26 に直した不具合

## 走らせ方

```bash
npm run e2e:hotkey
```

`src-tauri/target/debug/nox-voice.exe` を実際に起動し、実キー相当の合成入力
(`SendInput`) を送って、**アプリのログに何が出たか**で判定する。設定 UI の操作は
WebView2 の CDP (`--remote-debugging-port`) から行う。

前提と副作用:

- **実設定ファイルを使う**。開始時に `config.json.e2e-backup` へ退避し、終了時
  (異常終了も含む) に必ず戻す。
- 走行中は `injection_enabled` を切る。合成キーで始まった録音の結果が
  利用者の作業中ウィンドウへ貼られるのを防ぐため。
- **送ったキーは前景アプリにも届く**。前景奪取は成功しないことが多い
  (バックグラウンドのコンソールから起動したプロセスは前景を取れない)。
  トリガーは物理キーボードに存在しない F13〜F15 を主に使うが、既定ホットキーの
  検証だけは Space を送る。**実行中はキーボードに触らないこと。**
- デバッグビルドは `frontendDist` ではなく `devUrl` を見るので、ハーネスが
  vite を起動する。上がっていないと画面が真っ白のまま起動し、エラーも出ない。

## 判定の 3 値: PASS / FAIL / SKIP

`T1` (既定 左Ctrl+Space) は**較正を兼ねる**。ここが通らない環境では合成入力が
フックまで届いていないので、以降のキー依存テストは `FAIL` ではなく `SKIP` と
書く。**SKIP は合格ではない。** その run はキー経路について何も測れていない。

この区別が要るのは、実測で「物理キーボードでは動くのに、合成入力だけがフックに
届かない」状態が起きたため。SKIP のまま報告を終えず、物理キーで切り分けること。

陰性側のテスト (`T2` Space 単独 / `T5` 旧ホットキー / `T7` Esc 取り消し) は、
**フックが死んでいても素通りする**。緑だけを見て安心しないこと。

## 直した不具合 (すべて陽性コントロール付き)

陽性コントロール = 修正を元に戻して、対応するテストが**実際に落ちる**ことを確認した。

### 1. 合成入力を一律で無視していた → 正当なユーザー入力まで捨てていた

`WH_KEYBOARD_LL` の `LLKHF_INJECTED` で弾いていた。このフラグは注入元を区別しない
ので、RDP・PowerToys Keyboard Manager・AutoHotkey 等を経由した**本物のキー入力も
全部無視**される。`dwExtraInfo` に載せた自プロセスの印だけで判別するようにした。

- 陽性コントロール: 一律除外に戻すと `T1 / T3 / T4 / T6` が落ちる (4/8 → 8/8)。
- `docs/design.md` に「将来こう直す」と書いてあった既知の制限を実装した形。

### 2. 捕獲 UI で設定した直後から、そのホットキーが効かない

捕獲は「押したキーを**すべて離した瞬間**」に確定する。その確定処理が、確定した
全キーを「離されるまで無視」リストへ登録していた。登録解除は keyup でしか起きない
のに、**その keyup はもう過ぎている**。結果、設定したばかりのホットキーが
アプリ再起動まで恒久的に無視される。

「設定は保存されるのに効かない」という報告の正体。押されたままのキーだけを
登録するよう変更した。

- 陽性コントロール: 修正を戻すと `T4` だけが落ちる。
- 回帰テスト: `hotkey::tests::keys_already_released_are_not_suppressed`。
- 既存の単体テスト 2 本が**古い挙動を正しいものとして守っていた**ので、
  「押されている」をテストから注入できる形に直した (`hold_keys`)。

### 3. フックが OS に無言で外される

コールバックの応答が `LowLevelHooksTimeout` を超えると、Windows は
`WH_KEYBOARD_LL` をチェーンから落とす。通知も無く `UnhookWindowsHookEx` も
呼ばれないので、**アプリは正常に見えたまま全キーが届かなくなる**(再起動で直る)。

15 秒ごとの生存確認を入れた。無操作の間だけ `VK_NONAME` (0xFC) を 1 打自分宛に
送り、自分のフックが観測できなければフックスレッドへ再設置を要求する。
フックスレッドは `THREAD_PRIORITY_TIME_CRITICAL`。

- 検出できていることの証拠: ログに
  `キーボードフックが応答しません … 再設置します` が実際に出る。
- **未解決**: 再設置しても合成入力が戻らない run がある。同じ状態でも
  **物理キーボードでは正常に動く**ことを実測で確認済み (2026-08-26)。
  合成入力側の制約 (注入元プロセスの整合性レベル等) が疑わしいが未確定。

### 4. 多重起動していた

単一インスタンスの仕組みが無く、実際に 2 プロセス同時稼働を観測した。
トレイ常駐はウィンドウが見えないので気づけない。二重に起動すると:

- フックが 2 本刺さり、1 回の押下で**録音が 2 回**始まる
- 片方で設定を変えても、もう片方は古いホットキーで反応し続ける
- 設定ファイルとログファイルを奪い合う (**ログが切り詰められるのを観測**)

`tauri-plugin-single-instance` を、他のプラグインより前に登録した。

- テスト: `T8`。

**2026-08-27 追記**: プラグインだけでは漏れることが分かった (起動競合と昇格レベルの
不一致。詳細は `docs/design.md`「多重起動の確実な防止」)。`run()` の 1 行目で
名前付きミューテックスを取るようにし、実プロセス 2 個での確認は専用ハーネス
`e2e/single-instance.mjs` (`npm run e2e:single-instance`) に分けた。
このハーネスも開始時に `nox-voice.exe` を全部落とすので、**アプリを使っている間は
走らせないこと**。なお `hotkey.mjs` は起動前に taskkill するため、ミューテックス化の
影響を受けない (「既に起動中」と判定されて即終了することはない)。E2E 用の
抜け道は用意していない — 常用の抜け道は本番でも付けっぱなしになりうるため。
