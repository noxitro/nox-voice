# ホットキー経路の E2E と、そこで直した不具合 (2026-08-26 / 08-28)

## 走らせ方

```bash
npm run e2e:hotkey
```

`src-tauri/target/debug/nox-voice.exe` を実際に起動し、実キー相当の合成入力
(`SendInput`) を送って、**アプリのログに何が出たか**で判定する。設定 UI の操作は
WebView2 の CDP (`--remote-debugging-port`) から行う。

前提と副作用:

- **実設定ファイルを使う**。開始時に `config.json.e2e-backup` へ退避し、終了時
  (異常終了も含む) に必ず戻す。
- 走行中は `injection_enabled` を切る。合成キーで始まった録音の結果が
  利用者の作業中ウィンドウへ貼られるのを防ぐため。
- **送ったキーは前景アプリにも届く**。前景奪取は成功しないことが多い
  (バックグラウンドのコンソールから起動したプロセスは前景を取れない)。
  トリガーは物理キーボードに存在しない F13〜F15 を主に使うが、既定ホットキーの
  検証だけは Space を送る。**実行中はキーボードに触らないこと。**
- デバッグビルドは `frontendDist` ではなく `devUrl` を見るので、ハーネスが
  vite を起動する。上がっていないと画面が真っ白のまま起動し、エラーも出ない。

## 2 つの入力経路 (2026-08-28 から)

キー捕獲が DOM の `keydown` / `keyup` へ移ったので、ハーネスが送るキーも
**2 系統**になった。どちらで送るかがそのままテストの意味を決める。

| 経路 | 送り方 | 通る道 | 使うテスト |
|---|---|---|---|
| フック経路 (PTT) | `SendInput` (`send-keys.ps1`) | OS → `WH_KEYBOARD_LL` → Rust | T1 / T2 / T4 / T5 / T6 / T9 |
| DOM 経路 (捕獲) | CDP (**接続直後に実測して**選ぶ、下記) | webview → `src/main.ts` → invoke → Rust | T3 / T7 / T10 |

DOM 経路の送り方は**決め打ちしない**。`Input.dispatchKeyEvent` はレンダラの
入力パイプラインを通るので本来こちらが望ましいが、WebView2 では **`code` が
空のまま DOM へ届く**ことが実測で分かった。捕獲は `event.code` だけを見るので、
Esc が `Unidentified` になって取り消しが効かず、`T7` が捕獲を開いたまま素通りし、
その残骸が次の `T10` を巻き添えにして落ちた。

そこで `T0` で **1 打送って `code` が届くか確かめ**、届かなければ
`KeyboardEvent` の合成へ落とす (`Cdp#detectKeyTransport`)。どちらを使ったかは
`T0` の結果行に出る。**どの経路で緑になったのか分からない緑は信用しないこと。**

同じ理由で、**捕獲を始めるテストは「キー捕獲モード: 開始」のログが出たことを
必ず判定に含める**。前のテストが捕獲を開いたまま終わると、次のテストの
`#hotkey-capture` の click は「畳んで終わり」になり、キーがどこにも届かないまま
素通りで緑になる。

DOM 経路を CDP から入れるのは、**DOM へ届くにはアプリのウィンドウが前景で
なければならない**ため。このハーネスはバックグラウンドのコンソールから
起動するので前景を取れないことが多く、`SendInput` の合成キーは前景の
別アプリへ行ってしまい捕獲には 1 打も届かない。CDP なら前景に関係なく
webview の入力経路へ入れられる。

この作りの帰結:

- **捕獲系テストはフックの生死に依存しない。** `T1` が SKIP になる環境でも
  `T3 / T7 / T10` は判定できる (だから `needsInjectedKeys = false`)。
  これは仕様どおり — 捕獲をフックから切り離したのが今回の修正そのもの。
- **測れないこと**: 物理キーが OS → WebView2 → DOM と届くこと自体。
  ここは前景を取れる実機でしか確かめられない。`T3` が緑でも、
  **実機で設定ウィンドウを前面にしてキーを押す確認は省けない**。
- 同じ理由で、Win キーとの組み合わせ・PrintScreen のように OS が先に
  処理してしまうキーが「捕獲できない」ことも、ここでは再現できない。

## 判定の 3 値: PASS / FAIL / SKIP

`T1` (既定 左Ctrl+Space) は**較正を兼ねる**。ここが通らない環境では合成入力が
フックまで届いていないので、以降のキー依存テストは `FAIL` ではなく `SKIP` と
書く。**SKIP は合格ではない。** その run はキー経路について何も測れていない。

この区別が要るのは、実測で「物理キーボードでは動くのに、合成入力だけがフックに
届かない」状態が起きたため。SKIP のまま報告を終えず、物理キーで切り分けること。

陰性側のテスト (`T2` Space 単独 / `T5` 旧ホットキー) は、
**フックが死んでいても素通りする**。緑だけを見て安心しないこと。
`T7` (Esc 取り消し) は DOM 経路になったので、いまは「取り消しログが出たこと」も
併せて見る (何も起きなかっただけの素通りと区別するため)。

## 直した不具合 (すべて陽性コントロール付き)

陽性コントロール = 修正を元に戻して、対応するテストが**実際に落ちる**ことを確認した。

### 1. 合成入力を一律で無視していた → 正当なユーザー入力まで捨てていた

`WH_KEYBOARD_LL` の `LLKHF_INJECTED` で弾いていた。このフラグは注入元を区別しない
ので、RDP・PowerToys Keyboard Manager・AutoHotkey 等を経由した**本物のキー入力も
全部無視**される。`dwExtraInfo` に載せた自プロセスの印だけで判別するようにした。

- 陽性コントロール: 一律除外に戻すと `T1 / T3 / T4 / T6` が落ちる (4/8 → 8/8)。
- `docs/design.md` に「将来こう直す」と書いてあった既知の制限を実装した形。

### 2. 捕獲 UI で設定した直後から、そのホットキーが効かない

捕獲は「押したキーを**すべて離した瞬間**」に確定する。その確定処理が、確定した
全キーを「離されるまで無視」リストへ登録していた。登録解除は keyup でしか起きない
のに、**その keyup はもう過ぎている**。結果、設定したばかりのホットキーが
アプリ再起動まで恒久的に無視される。

「設定は保存されるのに効かない」という報告の正体。押されたままのキーだけを
登録するよう変更した。

- 陽性コントロール: 修正を戻すと `T4` だけが落ちる。
- 回帰テスト: `hotkey::tests::keys_already_released_are_not_suppressed`。
- 既存の単体テスト 2 本が**古い挙動を正しいものとして守っていた**ので、
  「押されている」をテストから注入できる形に直した (`hold_keys`)。

### 3. フックが OS に無言で外される

コールバックの応答が `LowLevelHooksTimeout` を超えると、Windows は
`WH_KEYBOARD_LL` をチェーンから落とす。通知も無く `UnhookWindowsHookEx` も
呼ばれないので、**アプリは正常に見えたまま全キーが届かなくなる**(再起動で直る)。

15 秒ごとの生存確認を入れた。無操作の間だけ `VK_NONAME` (0xFC) を 1 打自分宛に
送り、自分のフックが観測できなければフックスレッドへ再設置を要求する。
フックスレッドは `THREAD_PRIORITY_TIME_CRITICAL`。

- 検出できていることの証拠: ログに
  `キーボードフックが応答しません … 再設置します` が実際に出る。
- **未解決**: 再設置しても合成入力が戻らない run がある。同じ状態でも
  **物理キーボードでは正常に動く**ことを実測で確認済み (2026-08-26)。
  合成入力側の制約 (注入元プロセスの整合性レベル等) が疑わしいが未確定。

### 4. 多重起動していた

単一インスタンスの仕組みが無く、実際に 2 プロセス同時稼働を観測した。
トレイ常駐はウィンドウが見えないので気づけない。二重に起動すると:

- フックが 2 本刺さり、1 回の押下で**録音が 2 回**始まる
- 片方で設定を変えても、もう片方は古いホットキーで反応し続ける
- 設定ファイルとログファイルを奪い合う (**ログが切り詰められるのを観測**)

`tauri-plugin-single-instance` を、他のプラグインより前に登録した。

- テスト: `T8`。

**2026-08-27 追記**: プラグインだけでは漏れることが分かった (起動競合と昇格レベルの
不一致。詳細は `docs/design.md`「多重起動の確実な防止」)。`run()` の 1 行目で
名前付きミューテックスを取るようにし、実プロセス 2 個での確認は専用ハーネス
`e2e/single-instance.mjs` (`npm run e2e:single-instance`) に分けた。
このハーネスも開始時に `nox-voice.exe` を全部落とすので、**アプリを使っている間は
走らせないこと**。なお `hotkey.mjs` は起動前に taskkill するため、ミューテックス化の
影響を受けない (「既に起動中」と判定されて即終了することはない)。E2E 用の
抜け道は用意していない — 常用の抜け道は本番でも付けっぱなしになりうるため。

### 5. キー捕獲がフックの脱落に巻き込まれて完全に沈黙する (2026-08-28)

実機ログで、捕獲モードに入ってユーザーがキーを押しても**フックからの捕獲
イベントがプロセス起動から累計 0 件**という状態が再現した。同じフックで
PTT (左Ctrl+Space) は動いており、捕獲ウィンドウの間には必ず
「生存確認のキーを観測できない → 再設置します」が挟まっていた。

原因は `WH_KEYBOARD_LL` の**無言の除去**。[LowLevelKeyboardProc][llkp] は
「Windows 7 以降、タイムアウトしたフックは呼ばれずに黙って外される。
外されたことをアプリが知る方法は無い」と明記している。しかもタイムアウトの
計測対象はコールバックの実行時間ではなく**フックスレッドへのメッセージ送達→
応答の往復全体**なので、コールバックがいくら速くても、CPU が飽和して
フックスレッドがスケジュールされなければ外される (`THREAD_PRIORITY_TIME_CRITICAL`
でも免除されない)。このマシンでは cargo ビルドと E2E を並行実行していた。

加えて構造的欠陥として **捕獲ウィンドウ 10 秒 < 番犬の周期 15 秒** があり、
「フックが死んでから番犬が気づくまで」に捕獲窓がすっぽり収まっていた。

対策は捕獲を DOM イベントへ移すこと (`docs/design.md` の同日の節)。捕獲は
設定ウィンドウにフォーカスがある場面の操作なので、グローバルフックを使う
必然性が無い。テスト側もこれに合わせて 2 経路構成にした (上記)。

- 回帰テスト: `hotkey::tests::capture_mode_mutes_the_ptt_path_entirely`
  (捕獲中に現行ホットキーを押しても録音が始まらない) /
  `dom_codes_map_to_the_virtual_keys_the_rest_of_the_module_expects` /
  `mapped_codes_round_trip_through_the_existing_labels_and_rules` /
  `an_unmappable_code_is_reported_rather_than_silently_dropped`。
- 疑似 E2E: `sim-ui.mjs` の `U2` (押して離すと確定) / `U2b` (使えないキーは
  理由を出して捕獲を続ける、2 回続けても終わらない) / `U2c` (捕獲ボタンの
  click 直後、**IPC 完了前**に押したキーも取りこぼさない)。

### 5-2. 捕獲開始が非同期で、その往復の間のキーが素通りしていた

上の修正の初版で踏んだ。`capturingMode` を `await invoke("start_hotkey_capture")`
の**後**で立てていたため、IPC の往復の間だけキーを受け付けられない時間帯が
でき、そこで押された Space が `preventDefault()` されずに捕獲ボタンを再発火させ、
**捕獲が即座に取り消されていた**。詳細と一般形は `docs/design.md`
「状態フラグを IPC の後にセットすると、その往復の間だけ無防備な時間帯ができる」。

- 回帰テスト: `sim-ui.mjs` の `U2c`。**モックの invoke に遅延を注入**して
  (`mock.delays[cmd]`)、click の応答を待たずにキーを押す。
- 陽性コントロール: 修正前に実際に落ちることを確認した
  (`downPrevented:false` / `activeElement:"hotkey-capture"`)。
  **モックが即座に解決するテストでは、この種の不具合は永久にすり抜ける。**
- 実機 E2E: `T3` (DOM 捕獲で設定) / `T7` (Esc 取り消し) / `T10` (Enter を拒否)。

[llkp]: https://learn.microsoft.com/en-us/windows/win32/winmsg/lowlevelkeyboardproc
